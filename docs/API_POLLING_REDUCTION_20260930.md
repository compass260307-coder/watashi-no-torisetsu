# APIの重複処理・定期確認の削減（2026-09-30）

## 変更内容

### 決済反映APIのリクエスト内共有

`/api/checkout/full-access-status` の `hasFullAccess` と購入履歴由来の権限を、それぞれ1つのPromiseとして同一リクエスト内で共有する。従来は自己診断・友達診断・運命の各判定から呼ばれ、各取得が最大3回重複していた。

`hasSelfReportAccess`、`hasTakoAccess`、`hasUnmeiAccess` は共有Promiseを任意で受け取る。他の呼び出し元の動作、関連メールアドレスの探索上限、旧購入者の権利、購入履歴のポリシー判定、クレジット復元処理は維持する。プロセスや複数リクエストで共有するキャッシュは追加しない。

実コードをin-memory DBで実行した代表例（クレジット復元関数内部のDB処理を除く）:

| 状態 | 変更前のDB参照 | 変更後 |
| --- | ---: | ---: |
| 未購入・メールなし | 15 | 9 |
| 未購入・メールあり | 26 | 16 |
| 購入完了・plan反映前 | 13 | 7 |
| 旧full・購入履歴なし | 9 | 5 |
| 旧tako単体購入 | 14 | 8 |

旧コミット`62603f9c`との18比較ケースで応答・HTTP状態・ヘッダー・クレジット復元の呼び出し回数が一致し、別ユーザー間で共有されないことも確認した。購入や返金の後の別リクエストでは新しい状態を取得する。

一過性DB障害時だけ挙動の差がある。最初の権限取得が失敗し、同じリクエスト内の後続取得だけ成功する状況では、従来は一部権限のみ解放される場合があった。変更後は最初の失敗結果を共有して安全側の未解放とし、次の確認リクエストで再取得する。

### 監視通信のライフサイクル

対象は現行画面から参照される以下の5コンポーネント。

- `PaidUnlockWatcher`
- `UnmeiClient`
- `UnmeiCheckoutConfirming`
- `ResultUpgradeGenerationWatcher`
- `ResultUpgradeChat`

共通の`startVisiblePolling`で、非表示時の次回予約を解除し、表示復帰時に即時確認する。実行中は次の確認を重ねず、コンポーネントの終了・再開始時にはAbortControllerで古い通信を中断する。すでに送信済みの通信は非表示だけでは取り消さず、その終了後の予約を停止する。

`ResultUpgradeGenerationWatcher`は、`failed`の間も2秒ごとのGETを続け、内部stateの変化で生成POSTを再送していた。変更後は失敗・完了・回答なし・権限なしで停止し、初回と手動再試行でのみ生成要求を送る。チャット側と同じ監視処理を使用し、通信失敗は連続5回、生成待ちは5分で既存の再試行案内へ移る。通常の確認間隔は2秒から8秒へ徐々に広げる。

手動再試行では、POST受付後にバックグラウンド処理が旧`failed`を更新するまで最大10秒の猶予を設ける。生成中を一度確認した後の新しい失敗は即座に停止する。

運命の生成監視では、既存の3〜8秒の確認間隔と自動再試行上限を維持し、古い応答による再生成・画面遷移を防ぐ。未購入・権限エラー・連続通信失敗では停止する。決済確認は初回1.2秒、その後2秒からの既存バックオフと解放条件を維持する。

画面を隠したまま初期化した場合は、表示して監視を開始した時点から待機期限を数える。運命の決済確認では購入反映後に生成を開始した時点から生成待ち期限を数え直す。

課金画面の初期読み込み、商品・価格、画面デザインは変更しない。
