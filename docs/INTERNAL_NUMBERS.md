# 社内向け数値画面 (/internal/numbers)

診断数・売上・ファネル・友達診断・シェアを、開いた時点の数字で見る社内向けの画面。2026-11-22 追加。

## 目的

これまでは Google スプレッドシートが 15 分ごとに生データを取りに来て、シート側で数えていた。数字が最大 15 分遅れ、1 日分のイベントを毎回運ぶため重かった。この画面は、開いたときと「更新」を押したときだけ、DB の中で数える。定期実行は使わない。

## 構成

| 役割 | 場所 |
|---|---|
| 表と集計関数 | `supabase/migrations/20261122140000_internal_numbers_dashboard.sql` |
| データの入口 | `src/app/api/internal/numbers/route.ts` |
| 画面 | `src/app/internal/numbers/page.tsx`、`src/components/internal/` |
| 型と表示用の計算 | `src/lib/internal-numbers.ts` |
| 閲覧の可否 | `src/lib/internal-numbers-access.ts` |

画面は DB 関数 `internal_numbers_dashboard` を 1 回呼ぶ。関数の中で次を行う。

1. イベントの時間別件数 (`metrics_event_hourly`) を「前回数えた時刻を含む時間枠から今まで」数え直して上書きする。足し込みではないので、連打や同時アクセスでも二重に数えない。同じ日は同時に 1 回しか数えない。
2. 診断・売上・友達診断・シェアは、元の表を直接数える。
3. 表示日と比較日 (既定は前日) の数字を返す。

日が終わって 5 分以上あとに数えた日は確定とし、以後は数え直さない。過去の日は、初めて開いたときに 1 日分を数える。

### 古い日は少しずつ数える

本番 DB は、キャッシュに載っていない古いデータの読み出しが遅い。1 日分のイベントを初めて読むと 1 分かかることがある (2026-11-22 に 64 秒を実測)。API からの呼び出しは制限時間で打ち切られるので、イベントは 1 時間分ずつ数え、1 回の呼び出しが約 2 秒を超えたら途中まで保存して返す (`metrics_event_days.is_partial`)。応答の `events_complete` が false の間、画面は自動で呼び直して続きを数えさせる。診断数と売上は元の表を直接数えるので、その間も正しい値が出る。

時間切れで失敗した呼び出しも、読んだ分は DB のキャッシュに残る。画面は 1 回だけ自動でやり直す。

## 数え方

利益ダッシュボード (スプレッドシート) に合わせている。

- 診断数: 診断を完了した人数 (`users.diagnosis_completed_at`、流入言語が日本語)
- 売上: 購入時刻で計上。日本円の決済のみ。テスト決済を除き、返金を引く
- 買い切り: 商品が `full_access` の件数。アップグレードは `premium_bundle`
- 広告流入: 流入元が `x` か `tiktok`。それ以外 (空欄を含む) は非広告
- 友達診断率・シェア率: その日に診断した人のうち、今までに友達の回答をもらった人・シェア操作をした人の割合。日がたつと増える
- ファネル: イベントの回数。セッション数は、その日の重複を除いた数

集計表には、ページ名や位置のような短い英小文字のラベルだけを入れる (`metrics_label`)。セッション ID や owner_token は保存せず、元に戻せないハッシュを 14 日間だけ持つ。

## 閲覧の許可

確認済みのログインメールが `internal_dashboard_viewers` にある人だけが開ける。許可する人を足すときは、Supabase の SQL Editor で実行する。

```sql
insert into public.internal_dashboard_viewers (email) values ('小文字のメールアドレス');
```

外すときはその行を削除する。権限がない人には、ページは案内だけを出し、データの入口は 404 を返す。

## まだ入っていないもの

- 広告費・利益・CPA (スプレッドシートから 1 日 1 回送る形で追加する予定)
- スプレッドシートや `show me` の読み先の切り替え
- ページ別・位置別のセッション数、バイラル係数、LINE 登録率
